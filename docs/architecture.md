# Architecture

| Piece | File | World | Job |
|---|---|---|---|

## Spectrum API (`src/lib/api.ts`)
- `POST https://robertsspaceindustries.com/api/spectrum<endpoint>`, JSON body, header `X-Rsi-Token: <Rsi-Token cookie>`. Anonymous visitors get a token too → public reads work logged out (verified 2026-10: `/auth/identify`, `/v2/forum/channel/list`, `/forum/channel/threads`, `/forum/thread/nested`).
- Background reads the cookie via `browser.cookies` (permission `cookies`); content script reads `document.cookie`.
- Friends: `friendsData()` reads `/v2/relationship/friend/list` + `/v2/relationship/friend-request/list` (what Spectrum's own friends sidebar uses), falling back to `/auth/identify` `friends[]`/`friend_requests[]` (legacy — empty for some accounts, which broke the first version). Normalizers in `src/lib/relationship.ts`. Writes try `/v2/relationship/*` then v1 `/friend/remove`, `/friend-request/*` — **unverified live**. The hub shows which source answered (+ warnings on hover).
- Endpoint list was extracted from Spectrum's bundle (`static.robertsspaceindustries.com/spectrum/static/bundle-*.js`). Payload normalizer (`src/lib/capture.ts`) accepts v1 snake_case (verified) and v2 camelCase (unverified).

## Read tracking (`src/lib/read.ts`, `local:read`)
- Per thread id `{replies, seenAt, at}` written when a thread page's payload arrives (or from list data on SPA navigation). Never moves backwards. Capped at 5000 most recent.
- Row status: unseen / read / new (+N = replies_count − seen). Jump-to-first-new = earliest loaded reply with `time_created > seenAt` → `/thread/<slug>/<replyId>`.
- Local only — independent of Spectrum's own server-side unread dot.

## Rows & replies (`decorate.ts`)
- List rows have no stable class: a row = ancestor of a thread link that has a sibling linking to a *different* thread. Only slugs seen in a captured list payload are painted (sidebar/bookmarks untouched). Classes `sp-row sp-read|sp-new|sp-unseen sp-muted sp-dev-row sp-watched sp-pinned`.
- Replies: `.forum-thread-item` (own `.forum-thread-member-info .nickname-separator` → handle). Muted → own `.body-content-blocks` hidden + "show" button. Hover actions: Mute, Watch author.
- **Unverified live** (no logged-in DOM capture yet): row detection, `.body-content-blocks`, wide/compact selectors.

## Mutes (`src/lib/filters.ts`)
- Authors by lower-cased handle; keywords substring or `/regex/` (always `i`, never `g`); labels by name; optional bump muting (latest reply by muted author). Pinned threads never muted.

## Watches + feed (`src/lib/watch.ts`)
- Threads: `/forum/thread/nested` → replies grew → event `replies:<id>:<count>`. Opening the thread page syncs the count (no notification for replies you read).
- Channels: newest page; first poll = silent baseline (`lastThreadId`). New thread by dev (`tracked_post_role_id`/`isGM`) or watched author → event; `allThreads` → every thread. Older thread whose `latest_activity` is a dev (`highlight_role_id`) or watched author → `reply:<id>:<time>`.
- Authors are only seen inside watched channels (Spectrum has no per-author feed endpoint).
- Keywords (`Watches.keywords`: `{ pattern, channelId | null, addedAt }`): `keywordsFor(w, channelId)` = the channel's own + every-channel patterns, passed to `channelEvents` as its 6th arg; a *new* thread whose subject matches (`keywordMatcher` from filters.ts, substring or `/regex/`) → event kind `keyword` (`dev` / `author` win the label when both apply, `allThreads` still emits `thread`). Bumps are not matched (star the thread for replies). Seen only in watched channels, like authors — the Watching panel watches a channel picked as scope. Spectrum list rows a keyword would catch get `sp-keyword` (purple inset edge, title).
- Feed `local:feed`: deduped by key, newest first, max 300. Max 5 notifications per poll.
- Scheduling: `schedule()` in the background creates the poll alarm every `pollMinutes` (≥ 2) or clears it when `Settings.pollAuto` is false (passive: only `poll:now` from the Feed / popup runs `doPoll`, which also covers the store wishlist refresh and the friends snapshot). The party alarm is separate and unaffected.

## Friends (`src/lib/friends.ts`, `src/lib/orgs.ts`)
- Source: see Spectrum API above (v2 relationship list, identify fallback). Requests normalized to `requesting_member_id`/`target_member_id`/`status`.
- **Added time**: Spectrum has no friendship date (bundle checked: only pending requests carry `createdAt`). `touchNotes()` on every poll + hub load: the very first snapshot marks existing friends `firstSeen: 0` ("before Spectrum+"); friends appearing later get `firstSeen = now`. Accepting a request in the hub stamps it immediately.
- **Unfriend / re-add**: friends missing from a non-empty list (or unfriended in the hub, `markRemoved`) get `removedAt`; when they reappear they count as newly added (`firstSeen = now`, party cleared, tags/note kept). An empty list never marks anyone removed.
- **Party**: `party` flag in `local:friendNotes`; `partyEvent()` emits one feed reminder per set of due party friends after `partyRemindHours`, counted from the add time, or from `partyAt` (when marked) if the add time is unknown.
- **Orgs**: main org = member badge with `/orgs/<SID>` url (free). All orgs = `GET /citizens/<handle>/organizations` (public HTML, regex-parsed: `box-content org main|affiliation`, `visibility-R|H` = redacted), ~1 req/s, hub fetches in batches of 10, `local:orgs` TTL 24 h.

### Incognito
Manifest `incognito: 'split'`: incognito windows get their own background worker, hub and popup, and cookie jar (so a second RSI login works there). `chrome.storage` is shared, so `settings.ts` puts **account data** under `incognito.` keys when `INCOGNITO` is true: read, watches, feed, friendNotes, presence, seenRequests, hangar, buyback, partyMode, partyLog, lastPoll. Shared by both: settings and mutes, orgs cache, store catalog, wishlist. The incognito background runs (polls, party mode) only while an incognito window is open; incognito data persists across sessions. Enable via chrome://extensions → Allow in Incognito. Split in dev too: spanning would put the hub in a normal window even when opened from incognito (Chrome shows no extension pages in incognito windows under spanning) and share one cookie jar. WXT's hot reload registers content scripts from both backgrounds; the loser's "Duplicate script ID" rejection is harmless and swallowed in `background.ts` (dev only). The hub opens in the requesting window (`hub:open` carries the popup's `windowId`; content scripts use the sender tab's).

## Hangar & buyback (`src/lib/hangar.ts`, `src/lib/account.ts`)
- Row fields (markup checked on a saved `/account/pledges` copy, 2026-10-15): hidden inputs `js-pledge-id` / `-name` / `-value` / `-configuration-value` / `-currency` ("Store Credit" or a cash currency → `paidWith`) / `-not-buybackable` (→ `noBuyback`) / `-last-alpha` (ignored), JSON scripts `js-pledge-nameable-ships` / `js-pledge-name-reservations` (→ `nameable`, `reservedNames` via `jsonNames`, shape defensively string-or-object), `.availability` text (kept only when not "Attributed"), `.item-image-wrapper .image` for the row picture and `.items .item > .image + .text > .title / .kind` for items. All optional on `Pledge` so old saves keep working; `stackKey` ignores them.
- Item thumbnails: `parseItems` keeps `PledgeItem.image` from `.item .image` (`background-image:url(…)`, or an `<img src>`) via `imageOf()`; plus the row's own picture as `Pledge.image` (first `.image` not inside `.items`); `inventory()` carries the item's picture, else the pledge's when the pledge holds just that one thing besides insurance, as `ItemRow.image`, and Paints by ship falls back to it when `storePaintFor` finds no listing (paints the store stopped selling). The hangar HTML for items was not captured live — verify after a reload. The Star Citizen Wiki API (`api.star-citizen.wiki/api/v2/items?filter[type]=Paints`, anonymous) lists paints but `images: []`, so no third-party source is used.
- Loaded **from the hub page** (DOMParser available; session cookies via host permission): `/account/pledges?page=N&pagesize=50`, `/account/buy-back-pledges?page=N&pagesize=50`. Stops on an empty page, a page with < 10 items, or a repeated first id (RSI repeats the last page). 429 → retry with backoff.
- Hangar selectors per HangarXPLOR (MIT, 2026-04): `.list-items > li`, `.js-pledge-id|name|value`, `.js-upgrade-data` JSON, `.items .item .title/.kind`, `.js-reclaim`, `.label` "Gift", `.upgraded`, `.custom-name-text`, `.date-col`.
- Buyback parser is **defensive / unverified**: `article.pledge` (or list items), heading, `dt/dd` (Last Modified, Contained), `[data-pledgeid|fromshipid|toshipid]`, `a[href*=buyback]`. The list page gives contents only as "5 items"; **each entry's own page** (`/pledge/buyback/<id>`, verified from a saved page 2026-10-13) lists them: `parseBuybackDetail` reads `.package-listing.ship ul li` (ships), `.package-listing.item ul li` (*Also Contains*), `.final-price[data-value]` (buy-back price today, cents — the pack's current store price, e.g. a 4-paint pack at −20 %), `.original-price`, `a.js-buy-back[data-sku]`, `.buy-back-warning strong` (tokens left). `account.loadBuybackDetails` fetches one page per entry without `items` (350 ms apart, 429 backoff, saved every 5) → `BuybackItem.items / contained / price / listPrice / sku / detailAt`; Buyback tab button *Load contents & prices (N)*, price shown under *Buy back*.
- Cached in `local:hangar` / `local:buyback` only — never synced or sent anywhere. Saved after **every page** (`complete: false`, `page`) as a plain JSON copy; the panels offer *Resume from page N+1*. `unlimitedStorage` lifts the 10 MB `storage.local` quota.

## Store catalog (`src/lib/store.ts`)
- `matchShip`: exact key → longest catalog name contained in the text → (hangar names drop model codes) the shortest catalog name that is the text with only a model code in front ("Wolf" → L-21 Wolf, "Hornet" → F7C Hornet; never L-22 Alpha Wolf) (words no catalog name uses, like "Starlifter" in "Hercules Starlifter C2", are ignored) → last resort, the same words once model codes are dropped on both sides ("F7A Hornet Mk II", not sold, → F7C Hornet Mk II; never a Mk I).
- `POST /pledge-store/api/upgrade/graphql` (array body). `initShipUpgrade.ships` = all ships, `msrp` in cents, standalone `skus` — works with no session. Upgrade targets `to(from)` need `POST /api/account/v2/setAuthToken` (+ `setContextToken`) first — no CSRF. Unused declared GraphQL variables → HTTP 400.
- Target sku price is absolute; CCU A→B costs `sku.price − msrp(A)` (RSI's `upgradePrice`). One `to(from: cheapest)` query yields every target.
- Background refreshes every 30 min with a wishlist, else 6 h (`local:catalog`); `wishlistEvents` alerts on the first offer or a lower one (`sync:wishlist.lowest`).
- Verified live 2026-10: 240 ships, 53 CCU targets on sale, warbond detection. 2026-10-16: 241 hulls, every one with an MSRP, 89 with a standalone SKU on sale.
- Sale history (`local:saleHistory`, `SaleHistory` = per ship id `{ ccu?, standalone? }` ms): `recordSales` stamps what is on sale on every catalog refresh (`background.catalog()`), `lastSale` reads the latest. Starts empty at install — RSI publishes no sale calendar — and feeds "not on sale · last <date>" in the Ship catalog and the planner's `future` rows.
- Hub page *Ship catalog* (`#store`, `StorePanel`): defaults to what the store sells now — an *On sale · N / Not on sale · M / All hulls* segmented control (on sale = a CCU to the hull or a standalone), header counts on-sale ones; filters add *Concept ships*, owned / not owned, maker; *Plan CCU* on a not-on-sale hull links `#ccu?to=<id>&ahead=1`.

## Hub navigation (`hub/Hub.svelte`, `src/lib/hub-hash.ts`)
- **Flat sidebar: one entry = one page = one hash, no second-level tab bars.** Spectrum: Feed, Watching, Friends, Mutes. Hangar: *Pledges* `#hangar`, *Melt calculator* `#melt`, *My ships* `#fleet`, *Paints by ship* `#paints`, *My items* `#items`, *Buyback* `#buyback`, *Wallet* `#wallet`. Store: *Ships for sale* `#store`, *Browse* `#browse`, *CCU planner* `#ccu`, *Paint rebuy* `#paint-rebuy`. *Settings* `#settings` is the gear in the header (15 nav entries + the support footer already fill an 800px window; nav rows are one line, the subtitle is the hover title and the header's second line). Naming rule: "My …" = yours (hangar side), "… for sale" / Browse = the store. `HubTab` in `messages.ts` is the union the popup, SiteBar and notifications use.
- Panels that used to hold a tab bar take the page as a prop and stay mounted across their pages: `HangarPanel pane="pledges|melt"` (one instance, so melt ticks and filters survive switching), `ShipsPanel view="paints|ships|bundle"` (My ships → "paints for this hull" just sets `location.hash = '#paints'`). `StorePanel` is the ship catalog only; the former Items tab is `BrowsePanel`.
- `legacyHash()` maps pre-flatten hashes on load and on `hashchange` (`history.replaceState`): `#hangar?view=melt` → `#melt`, `#ships[?view=…]` → `#paints` / `#fleet` / `#paint-rebuy`, `#store?view=items[&cat=…]` → `#browse[?cat=…]`, `cat=concierge|subscribers` → `who=`. Tested in `tests/hub-hash.test.ts`. `localStorage` `rsiplus:hangar` / `rsiplus:ships` no longer remember a pane / view (the hash is the state).

## RSI cart (`src/lib/cart.ts`)
- Upgrades: `POST /api/ship-upgrades/setContextToken {fromShipId, toShipId, toSkuId[, pledgeId]}` (pledgeId = buy-back mode) → `getPrice(from: shipId, to: skuId) { price { amount } }` (cents) → `mutation addToCart(from, to) { jwt }` on `/pledge-store/api/upgrade/graphql` — a **ticket**, not a line → `POST /api/store/v2/cart/token { jwt }` (platform API, `X-Rsi-Token`) and only its `success: 1` means the line is in the cart. Mode guard before adding: `app { mode }` must be `buyback` for a buy-back (after a context with `pledgeId`) and must not be `buyback` for a normal upgrade. Sign-in check first: `setAuthToken` + `setContextToken` **with `X-Rsi-Token: <Rsi-Token cookie>`** (RSI's `attachStoreHeader`; without the header the platform API mints an anonymous account token even when signed in — the JWT is bound server-side to the session, no cookie comes back), then `initShipUpgrade { app { isAnonymous } }`. Sources: RSI's store bundle (`rsi.store.build.*.js`) and Open Hangar's cart PRs #396/#404 (API shape only — their code is PolyForm Strict, nothing copied).
- **Buyback compare** (`buybackCompare(buyback, rows, fleet, ships, storeIdx)`): each saved buyback entry's contents (`contained`, else its name) vs hangar item titles → paint-only entries whose paint you lack split into *for ships you own* (hull line owned, variants count) / *other*, with the store listing today and copies in buyback; other entries with at least one item you lack → *items you don't have* (+ what you still have); entries owned again counted; CCUs skipped (planner). `storeLinksFor(titles, ships, storeIdx)` → store pages (+ price today) for paints in stock and ships with a standalone SKU on sale; `BuybackMissing.store` carries them and `buyableNow` = every missing item has one → hidden by the *hide what the store sells today* toggle (default on, pref `bbHideStore`); the missing items render as 🛒 links. *I own it* per row marks a buyback entry as already owned (pref `bbOwned`, by buyback id) — hidden from all three views, *show marked as owned* lists them to undo. RSI's buyback page often lists a pack's contents as just "5 items": `countOnly` / `buybackContents` → `[]`, `packHint(b, rows, ships)` names the hull from the entry name and lists your hangar paints for that hull line — shown as *contents not listed · N items* + "You own K <Hull> paints: …" on the Buyback tab (own filter value *Contents not listed*) and as a sub-table in the compare's *Items I don't have* view (`BuybackCompare.unknown`). `hangarCounts(pledges)` = copies per item title in the saved hangar; the compare shows ×N on what you still have and an *Already in hangar* view (`ownedAgain`). The **Buyback tab** has an *In hangar* column (in hangar ×N / N of M / not in hangar; packs list **Not in hangar: …** in red and what you have with counts) with an *In hangar: any / already (every item) / partly / not (none of it) / contents not loaded* filter (a count-only pack counts as *already* when you own at least as many paints for its hull as it has items), with the store link + today's price inline on each missing line (single-item entries: beside the badge) and a "Missing on the store: $X · buy back: $Y → cheaper" line; `StoreLink.sku` (paint listing id / cheapest standalone SKU) feeds **+ cart** per missing line and **Add all missing to cart** per pack (`cart.addStandalone`, sequential, never retried; *Open RSI cart* appears once something is in); the *only entries the store sells today* filter stays with the same links per entry and an *only what the store sells today* filter (reads `local:catalog` + `local:paints`). Folded section *From your buyback* on the tab, fed from `local:buyback`.
- **Melt checklist** (panel, `localStorage` `rsiplus:paintbundle:melt`): *Start checklist* freezes the plan (rebuy picks + melt-only) as items {id, name, titles, credit, why, hangar page}; rows grouped by hangar page with *open page ↗* and *melt ↗*; tick by hand, or a pledge missing from a reloaded hangar ticks itself (*gone from hangar*); progress bar + credit melted so far. Editable: *+ checklist* / *listed* on every rebuy-candidate and melt-only row (a candidate added is picked too, so its paints join the cart plan, and the list drops back to *unconfirmed* so the cart gets re-checked), ✕ per row, *Add today's picks (N)* merges the plan in, *Replace with plan* resets to it, *Clear*. Filters: search + To melt / Melted / All / Rebuy / Melt only. *Reload hangar* reloads in place (`lib/hangar-refresh.ts` `refreshHangar` — same pages and `hangarItem` as the Hangar tab, progress on the button; the CCU planner's *Load hangar* uses it too).
- **Read the cart**: `readCart()` = `POST /graphql` `MiniCartWidgetQuery` (from `static.robertsspaceindustries.com/pledge-store/index.*.js`, 2026-10; `x-csrf-token` from the cart page) → `CartSnapshot` {id, subTotal, total, qty, lines[{skuId, qty, title, unit, unitDiscounted, discount wording, discounts[], upgrade}]}. The paint panel's **Confirm cart** compares it with the planned lines (✓ / ✗ per SKU + qty, extras flagged), shows RSI's real per-line discount and the observed rate vs the planner's assumption, and says *safe to melt* only when every planned line is there. Also how the open questions (tier on sale price, pack lines) get answered: add, confirm, read the discount column. Unverified live until first use.
- Standalone ships: `POST /graphql { query: 'mutation AddCartItemMutation { store(name:"pledge") { cart { mutations { add(skuId, qty) } } } }' }` with `x-csrf-token` from `<meta name="csrf-token">` of `/en/store/pledge/cart`.
- Rules: `addToCart` is never retried (a lost answer may still have added the line); errors classified `signed-out` / `conflict` (message mentions cart / buy-back / pending / invalid — RSI blocks new lines while a pending order or a buy-back sits in the cart) / `network` / `refused`. Buy-back needs a `toSkuId`: the target's current standard CCU SKU from the catalog (RSI's buy-back list doesn't expose it) — unverified. **Not live-verified yet** (see now/todo).
- Verify: `verifyUpgrade` = context → `from(to: skuId) { ships { id } }` (every ship RSI lets you upgrade from to that SKU — the planner only knows prices, not RSI's eligibility rules) → `getPrice`. Panel *Verify chain with RSI* runs it per step (300 ms apart) and badges ✓ / ⚠ price / ✗.
- Panel: per-step button + *Add N store steps* (sequential, 400 ms apart, stops at the first error; buy-backs skipped), per-step state (adding / in cart + RSI price / error code), *Open RSI cart ↗*. Nothing checks out.

## CCU planner (`src/lib/ccu.ts`)
- Dijkstra over catalog ships (msrp > 0), ties → fewer steps. Edges: on-sale CCU SKUs (`warbond` / `standard` / `limited`, sold-out limited skipped), owned hangar CCUs (cost 0), buyback CCUs (optional, cost ≈ msrp diff).
- Owned CCUs mapped via upgrade JSON ids when the catalog id's name agrees, else `matchShip` (normalized names, longest contained catalog name). Unmatched shown in the panel.
- **v2 (CCU Game parity, spec [plans/specs/ccu-planner-v2](plans/specs/ccu-planner-v2.md))**: `objective` = `spend` (owned CCUs free; CCU Game "current savings") / `cash` (least new money first — warbond + anything store credit can't pay — then spend) / `longterm` (owned CCUs cost their melt value). Ranking is lexicographic (`rank()`), ties → fewer steps.
- Source modes: hangar ship / any ship / **store** (`startId = STORE_START = 0`: virtual node with one `standalone` edge per ship with a standalone SKU on sale; baseline = target MSRP).
- Options: `storeCredit` (off → every step is new money), `excludeGifted` (hangar CCU with melt value 0 = gift), `include[]` (forced CCUs, routed through in MSRP order as segments; null if a leg is impossible), `exclude[]` (force exclude + refs reserved by saved chains, `reservedRefs()`).
- Saved chains: `local:ccuChains` (per account, in `ACCOUNT_ITEMS`), `SavedChain` = name, start/target, steps, totals, options. The panel re-prices each on today's data (other chains' CCUs excluded) and flags drift. "Your CCUs" table = CCU Game's CCU Overview with per-row force include / exclude / auto cycling.
- **Plan ahead / long-term goals** (spec [plans/specs/ccu-long-term](plans/specs/ccu-long-term.md)): `opt.planAhead` adds a `future` edge to every hull with no usable CCU SKU today at MSRP (`cost = msrp(B) − msrp(A)`, no `skuId`; store credit unless off). `rank()` puts `waits` (future-step count) before step count in every objective, so waiting never beats buying today at the same price. `Plan.waits` / `Plan.later` split *to pay now* from *later*. `cart.addable` → none for `future`; the panel's verify marks them `wait`. `chainEvents(chains, ships, now)` (called from the poll's catalog refresh) emits `store` feed events (`hub.html#ccu`, key `ccu:<chain>:<from>><to>:<sku>`) when a saved chain's waited-for hull has an in-stock CCU SKU priced above its source hull — one per SKU appearance thanks to feed key dedup. `#ccu?to=<id>&ahead=1` (from the catalog's *Plan CCU* on a not-on-sale hull) starts with the option on.
- **Fleet plan** (spec [plans/specs/ccu-fleet-plan](plans/specs/ccu-fleet-plan.md), `CcuFleet.svelte`):
  - The planner toggles between *One chain* and *Fleet plan* (`rsiplus:ccu:planner`).
  - `planFleet` plans priority-ordered `Goal`s (target, source hull / `STORE_START` / `null` = auto, `via` stops). Earlier goals reserve their CCU refs and hull copies (`ownedHulls`).
  - Auto tries the free hull copies below the target (not `keep`), plus the store when allowed. It keeps the plan with the highest savings vs MSRP, then the least to pay now, then the fewest waits.
  - `PlanOptions.via` (stops) also works in the single planner. Stops and forced CCUs are walked in MSRP order.
  - Goals live in `local:ccuGoals`. *Save plan* writes one `SavedChain` per goal with `group`, replacing the same group.
  - *Open* loads a goal into the single planner for verify and cart.
- **Auto plan-ahead**:
  - When `plan()` with today's sales returns null and `planAhead` is off, the single planner re-plans with `planAhead: true` (`planned.ahead`, notice above the stats). The chain is saved with those options.
  - `planFleet` does the same per goal: its second pass is tried only when no candidate source works with today's sales, so a buyable-now chain always wins. That sets `FleetLeg.ahead`.
  - `ShipSelect saleTag` tags hulls with no available CCU / standalone SKU.
- **Extra hulls** (`src/lib/data/extra-ships.ts`): `EXTRA_SHIPS` covers Kraken, Kraken Privateer, Javelin and Idris-M.
  - Negative ids, `msrpSource: 'wiki'`, starcitizen.tools pledge cost, link to the wiki page.
  - `withExtraShips` adds them in `fetchCatalog` and on the background's cached catalog, unless RSI lists the name itself.
  - They have no SKUs, so they only appear as `future` targets. The planner shows no store link for them.
- **Per-goal options**:
  - `Goal.lti` (`any` / `prefer` / `only`) and `Goal.storeStart` (falls back to `FleetOptions.storeStart`; the old plan-wide value is migrated into goals on load).
  - `ownedHulls` counts LTI copies (`lti`). `planFleet` keeps free copies split `{ lti, plain }`: LTI goals take LTI copies, others take plain ones first.
  - Auto candidate groups: LTI hulls first for `prefer` (only those for `only`, which also never adds `STORE_START`), each split by the global `prefer` list.
  - `FleetLeg.lti` = the upgraded copy is LTI.
- *Want* pickers (fleet *Add a ship you want*, single *Target*) list only hulls you don't own unless *include ships I own* is ticked.
- **Fleet `prefer`**: auto candidates are tried in two groups, preferred hulls first, within each pass (today's sales, then plan ahead). So a preferred hull that gets there beats any other hull, but never beats buying today vs waiting.
  - `ccuGoals.prefer` is stored next to `keep`.
  - *+ my LTI hulls* = `ownedHulls` of LTI pledges.
- Not done: speculative prices (needs a price-history store), k-best alternatives, a sale calendar, a global optimum over goal order.

## Guided flows (`src/components/Wizard.svelte`)
- A vertical stepper fed by `WizardStep[]` that each panel **derives from its own state** — nothing is re-implemented: `done` is judged from live data (pledges loaded, picks, cart ledger, RSI cart read-back, verify results, saved chains, hangar reload), `blocked` withholds the action with a reason, `warn` flags a problem you can still act on, `action` is the panel's own handler or a link (`#hangar`, RSI cart). ## Fleet export (`src/lib/export.ts`)
- `xplorRows(pledges, ships)`: one row per ship hull in each pledge, in **HangarXPLOR's JSON shape** (its `Download.js`, MIT) — `ship_code`, `ship_name` (pledge nickname, else the ship), `manufacturer_code` / `manufacturer_name`, `name` (catalog name via `matchShip`, else the listed title with the maker prefix stripped), `lti`, `warbond`, `entity_type: 'ship'`, `pledge_id` (string), `pledge_name`, `pledge_date`, `pledge_cost` (`$45.00 USD`). Sorted maker → ship. CCU pledges contribute nothing.
- Why that shape: it is what FleetYards' importer reads (`app/lib/hangar_importer.rb` matches `item[:name]` against name / rsi_name / slug, `ship_name` → custom name, plus its own `hangar_xplor_mapping` for renamed hulls), what myfleet.gg (StarShip42 FleetView's successor) and Starjump / hangar.link import, and what the Hangar Transfer Format of Open Hangar extends.
- `shipCode(name, maker)`: HangarXPLOR's `ship-codes.json` vendored as `src/lib/data/ship-codes.ts` (305 hulls; exact name, else the name without "Mk N" — `Constellation Mk IV Andromeda` → `RSI_Constellation_Andromeda`); unknown hulls get `MAKERCODE_Name_With_Underscores` like HangarXPLOR's own fallback, maker code from the table (else the maker's first word upper-cased).
- `xplorCsv(rows)`: HangarXPLOR's CSV columns `Manufacturer,Ship,Lti,Warbond,ID,Pledge,Cost,Date`, text fields quoted with `"` doubled. `shipLines(rows)`: `Maker Ship` per hull for plain-list tools.
- UI: **My ships → Export fleet** menu (JSON, CSV, copy names) for the whole hangar; **Pledges → Fleet JSON (HangarXPLOR)** for the pledges currently shown (respects filters, like CSV / JSON there).

## Paint rebuy (`src/lib/paints.ts`, `PaintBundlePanel.svelte`)
- RSI's multi-paint cart discount (`PAINT_TIERS`: 2 → 15 %, 3 → 20 %, 5 → 25 %, 7 → 30 %, 10+ → 35 %; `paintDiscount(n)`, `nextPaintTier(n)`). Melting gives the full paid value as credit, so paints bought at full price can be melted and bought back in one cart for less.
- `rebuyCandidates(pledges, storeIndex, {packs, packCountsEach})`: **only pledges you can melt and rebuy today** — `canMelt` (meltable, value > 0), paint items only (`categorize`), every paint matched to a store listing (`paintKey`) that is `available`. Each candidate has up to two `RebuyOption`s: `single` (one listing per paint, each counts toward the tier) and `pack` (one pack listing; counts 1, or its contents with `packCountsEach`). Pack when the pledge name / lone item is a pack listing, or its singles are exactly a known pack's contents. Everything else is listed with a `SkipReason` (not meltable / $0 / other items in the pledge / not on store / out of stock).
- **Store packs** (`storePacks`): 2026-10 the store has 3 (890 Jump 3-pack, Keystone collection, Racing collection). Contents inferred from names (hull before " - ", or the collection word) and accepted only when the singles' list prices sum to the pack's list price exactly; `impliedRate` = 1 − pack price today ÷ singles sum — **packs are priced at the tier their paints would get alone** (890: 3 singles − 20 %, Keystone: 8 singles − 30 %), so a bigger singles cart beats a pack. `optionAt(c, rate, prefer)` = cheaper option at the rate (ties → singles); the planner tries both "cheapest" and "singles" preferences per tier.
- `bundleTotals(picks, wanted)`: lines = picks' store listings + wanted paints, rate from lines; `credit`, `list`, `pay`, `rebuyGain` (credit − discounted rebuy), `net` (+ what the wanted paints save by riding along vs their own tier). `planBundle(cands, wanted, limit = 50)`: per tier, rank by `gainAt(c, rate)`, take positive gains that fit under the cart cap, then least-negative ones only until the tier is reached; best `net` wins, ties → fewer melts. Cap default `CART_PAINT_LIMIT` = 50 (RSI cart), editable in the panel. `bundleScenarios(cands, wanted, cap)`: the best plan at each cart size (tier thresholds, then 15 / 20 / 30 / 40 / 50 and the cap; identical plans collapse) with `perPaint` = net ÷ lines; `bestScenario` = highest net.
- **Melt only** (`meltOnlySplit(pledges, rows, fleet, {noShip, duplicates})`, runs first; its `keep` feeds `rebuyCandidates`): meltable paint-only pledges whose paints all fit only ships you don't own (`no-ship`), or are all surplus copies beyond one per owned hull they fit (`duplicate`; copies are assigned in hangar order, a paint with no known ship is never surplus) → melt for credit, nothing to rebuy. Multi-paint pledges only when every paint qualifies. Both toggles default on; shown as its own table + tile, and in the headline "credit you end up ahead" (= rebuy net + melt-only credit).
- **Packs in the tier** (`packTier`, default `none`): unknown whether RSI discounts / counts a pack line. `none` = pack keeps its own price and counts 0 (safe); `one` / `each` = discounted and counts 1 / its contents. `optionPay(o, rate)` applies the rate only to `tiered` options.
- **Variants share paints** (`paintLine(name, ships)`): hulls are counted per line — the 100 / 300 / 400 series, else the name token shared with the most *other* catalog ships (L-22 Alpha Wolf → `wolf`, Constellation Andromeda → `constellation`, F7C-M Super Hornet → `hornet`; `items.family` would say `alpha`) — so a paint named for one variant counts as fitting every variant you own; *no-ship* means no hull of the whole line. Ship column: "fits your <variant>" when the exact hull isn't owned, hover = fits / line / hulls owned; a line lists hangar ships the catalog didn't match.
- **Dedupe across pledges** (`meltOnlySplit().redundant`): inside a kept pack, a paint already covered by another pledge (standalone or other pack, one copy per owned hull) or fitting no ship of yours is *redundant* → the panel auto-unticks it (`autoDrop`, chips *owned elsewhere* / *no ship*), `planBundle` / `bundleScenarios` take the `drop` map so plans price only what comes back; ticking it again overrides. *Deduped* show-filter.
- **Packs, rebuy all / some / none**: a pack pledge rebuys every paint in it as singles by default; each paint has its own checkbox in the row (`optionSubset` drops listings — melted, not bought back), a pack where only some paints are still sold is a candidate flagged `missing` (what is lost on melt; never auto-planned), and a melt-only pack row has *Rebuy instead* (`except` in `meltOnlySplit`). The planner melts a pack only when buying all its paints back is cheaper than its melt value — never as a loss-making tier-filler (singles may be); rows show *keep* otherwise.
- Hangar paint packs ("Idris - 5 Paint Pack", 5 items) are confirmed priced at their tier too (paid $86.25 = singles $115 − 25 %, user hangar 2026-10-13); most are no longer sold, so they rebuy as singles. `paidOff(c)` = how far under the singles' list price the pledge was paid (chip on the Paid column).
- Hover any paint thumb → fixed-position preview of the store's `slideshow.jpg` (same media id as the `store_small.jpg` thumb — the listing query is unchanged). Partial packs list each missing paint as a greyed *lost if you melt* line (with the store image when a listing exists but is out of stock) under the rebuyable ones; melt-only rows show thumbs too.
- Candidates table: search (paint / ship / pledge), *Show* chips (all / picked / not picked / gains / keep / packs / singles / partly on store / on sale), *Pick shown* / *Unpick shown*, sortable columns (`SortTh`: paint, ship, hangar, paid, alone, here, both gains; default gain-here desc); a Ship column from the items view's fits. Melt-only table: why chips + sortable, shares the search box.
- Per candidate the panel shows **Paid** (melt credit), **Alone** (`costAlone`: cheapest rebuy today, no tier), **Here** (chosen option × (1 − rate)) and both gains; pack / singles switch per row.
- Cart: store paint listing `id` **is the SKU id** (`__typename: TySku`, the same id resolves via `skus: {ids}` — checked 2026-10-13), so `cart.addStandalone(id, qty)` adds a paint line; added one per listing, 400 ms apart, stops at the first error. Melting stays on RSI (🏠 `melt ↗` = `hangarUrl(…, 'melt')`).

- UI: Store → *Paint rebuy* (`#paint-rebuy`, rendered by `ShipsPanel view="bundle"`): three money tiles (melt credit incl. melt-only → rebuy cost with "bundle saves vs list" → credit you end up ahead) + a one-line strip (paints in cart, tier, next tier, cap), options (cap, melt toggles, pack select) folded behind *Options*, a compact *Do it* row with the cart buttons, **Best value by cart size** table (★ highest net, *Use* applies that set), candidates table (auto-picked, tick to override, Auto-pick / Clear / Pick all), *New paints to buy* search (store paints not owned, count toward the tier), Do-it steps, *Add N paint lines to RSI cart*, *Open RSI cart*, folded "Not counted" list by reason. ## Melt (`src/lib/melt.ts`)
- `meltSummary(all, picked)`: credit (= sum of pledge values), items lost for good vs still owned via another kept pledge; LTI hull counts as its own thing; a CCU pledge counts as "upgrade A → B".
- `duplicatePlan(all)`: greedy by value — a pledge is pickable only if every item (and LTI hull) in it still has another copy among the pledges not yet picked; skips non-meltable, $0 (`canMelt`), CCUs, game packages. Result: melt everything redundant, lose nothing.
- `copiesElsewhere(all, picked, p)`: for a picked pledge, each item + the unpicked pledges still holding it ("✓ also in #123" / "✗ last copy").
- `DedupeOptions {types, keepLti, keep}` on `duplicatePlan` / `targetPlan` / `meltSummary` / `marginalLoss`: restrict pledge types, never pick LTI, and `keep` = item key → copies to keep. `items.paintCopiesNeeded` fills `keep` with one copy per owned hull a paint fits, so 3 Cutlass paints for 3 Cutlasses aren't duplicates; `MeltSummary.short` lists paints kept below that.
- `marginalLoss(all, picked, p)`: what melting `p` on top of the current picks loses (empty = pure duplicate right now).
- `targetPlan(all, usd)`: reach a credit amount losing the fewest unique items — duplicates first (highest value), then the pledge with the fewest additional losses (most $ per lost item as tie-break), then trim picks the target no longer needs. Never picks game packages. Greedy, not optimal — good enough for hangars of hundreds.
- UI: Hangar → **Melt calculator** page (`#melt`; *Pledges* `#hangar` is the same list without the tick / "Would lose" columns; both rendered by one `HangarPanel` instance, `pane` prop) — tick column, "Pick duplicates / Pick paints without a ship (paint-only pledges whose paints all have `paintStatus` no-ship) / Need $ → Plan for target / Pick shown / Clear", credit + lost/still-owned lists, per-row "Would lose" (−N chip, or *duplicate*), "Hangar ↗" per pledge.

## Versioning & releases

- Conventional commits drive semver while 0.x: `feat:` → minor, `fix:` / `perf:` → patch, `feat!:` / `BREAKING CHANGE` → minor (`bump-minor-pre-major: true`; `bump-patch-for-minor-pre-major` stays false, or features would only bump the patch). Other types (`docs:`, `ci:`, `chore:`) don't bump.
- release-please opens/updates a `chore(main): release X.Y.Z` PR that bumps `package.json` (the manifest version WXT emits) and `CHANGELOG.md`.
- Merging that PR creates tag `vX.Y.Z` and a GitHub release; the `assets` matrix job in `release.yml` attaches `rsi-plus-X.Y.Z-{chrome,edge,brave,firefox}.zip` plus `-sources.zip` (Firefox's AMO source bundle; `zip.excludeSources` drops `store/`, `docs/`). CI's `zip` matrix uploads the same four as artifacts.
- Browser targets (`wxt zip -b chrome|edge|brave|firefox`; brave and edge are the chrome MV3 build under their own name — WXT treats any non-firefox/safari target as MV3 Chromium): the manifest fn in `wxt.config.ts` branches on `browser === 'firefox'` — no `offscreen` permission, no `incognito: 'split'` (Firefox would install it as `not_allowed`; spanning instead, so private windows share the normal login and the `INCOGNITO` prefix only applies to pages opened from a private window), `browser_specific_settings.gecko` (id `rsi-plus@nylegarcia.github.io`, `strict_min_version` 128 for manifest `world: MAIN`, `data_collection_permissions: none`). Firefox builds MV2 (WXT default): `browser_action`, persistent background page → `lib/sound.ts` plays the ding in-page via `lib/ding-synth.ts` (shared with the Chromium offscreen document, which `<meta name="manifest.exclude">` drops from the Firefox build); `updateBadge` falls back to `browser.browserAction`. Not yet verified in a real Firefox (todo).
- **Pre-releases (`dev` branch)**:
  - Day-to-day work lands on `dev`. Every push there runs CI and `prerelease.yml`.
  - `scripts/next-prerelease.sh` works out the next version: the base comes from `.release-please-manifest.json`, the bump from the conventional commits since the last stable `v*` tag.
  - The workflow sets `package.json` to `<next>-dev<run:04>` in CI only (never committed), zips all four targets, and publishes GitHub prerelease `v<next>-dev<run:04>`. The run number is zero-padded because GitHub's releases page sorts tags as text (`dev.9` > `dev.13`); an alphanumeric identifier with leading zeros is still valid semver and compares right both ways. They are created with `--prerelease --latest=false`; the newest 10 are kept (the prune matches both `-dev.N` and `-devNNNN` tags).
  - WXT's `simplifyVersion` makes the manifest `version` `<next>`, and Chromium builds get `version_name` `<next>-dev<run:04>`. Firefox gets only `<next>`.
  - Real bumps: open a PR `dev` → `main`, merge, then release-please's PR → `vX.Y.Z` with assets as above.
  - Local builds (`wxt.config.ts` → `localVersionName`, not in CI, not on the tagged release commit) set `version_name` `<next>-dev (local <sha>[+])`, with `+` for uncommitted changes. WXT derives the manifest `version` `<next>` from it, so an unpacked `.output/chrome-mv3` shows it is newer than the last release.
  - `dev` is the GitHub default branch, and `release.yml` pins release-please to `target-branch: main`.
  - Branch protection:
    - `main`: no force push or deletion; status check `verify` required, not enforced for admins, because release-please PRs get no CI with `GITHUB_TOKEN`.
    - `dev`: no force push or deletion.
- CI does not auto-run on the release PR with the default `GITHUB_TOKEN` (GitHub limitation); re-run manually or switch to a PAT later.
- `docs/changelog.md` stays the hand-written user-facing log; `CHANGELOG.md` is generated.
